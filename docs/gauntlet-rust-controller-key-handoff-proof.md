# Worker-owned deterministic controller key: isolated handoff proof

The migration now has an opt-in handoff for a Rust-owned deterministic run. On Linux ARM, the internal Rust worker generates a fresh Ed25519 seed with `ring::SystemRandom`, writes it to a 32-byte Root-owned memfd, sets all four write/shrink/grow/seal seals, and keeps `FD_CLOEXEC` set in the parent. Under the existing exclusive worker lease, it first consumes the one-use job ID with a v2 started marker containing the public key, then writes an exclusive 0600 canonical `*.controller-key.json` sidecar bound to that exact job/source/deployment/worker-generation/started-marker digest and public key. The fixed `execveat` child clears `FD_CLOEXEC` for that descriptor only and receives its number through the exact additional environment key `HOL_GAUNTLET_RUST_SIGNING_KEY_FD`. The parent rechecks the marker and sidecar before returning from launch and after child cleanup; an orphan key sidecar blocks another reservation. Existing v1 markers remain readable and are never treated as keyed runs.

The Python adapter accepts that descriptor only for the deterministic profile on Linux as Root. It requires a decimal descriptor in the fixed range, a Root-owned unlinked regular file of exactly 32 bytes, all required seals and an offset of zero. It removes the environment selector, reads once, closes the descriptor, and supplies the resulting Ed25519 key to all six deterministic controls. With no descriptor, the existing Python execution path continues to create its own per-control key. The adapter is pinned at SHA-256 `ff3ece762f411439385fff86cc9ac017203f93a0ba0e4e63bae16ceceae2529b` (`ci_pipeline.py`), `e819cf846a62506a3b3523f4b6471d3fb5f85c117578fafc5a1746ef925b06ae` (`deterministic.py`) and `138160dc6daa77d1fed591f73cab240b0f3824529dcbb337f7ebb8bce6fc4777` (`deterministic_control.py`). The Rust key and outside-pinned reader modules are SHA-256 `a051c97c99f0390a2194ba37d396b84e26f5584ad59c630a8f703aa7af77c318` (`controller_key.rs`) and `eba458b5d03223fe4af6da49f841fcaa877ece20221784b629df034967216728` (`controller_key_observe.rs`) at this proof.

On the pinned ARM64 Rust 1.88.0 container, the key test passed: a sealed descriptor stayed closed across an ordinary exec, survived an explicit inert child handoff, and produced the expected public key from the child-read seed. A restarted journal read the same public pin; a duplicate pin, wrong started-marker hash, changed sidecar public key and stale key sidecar were refused. A v1 marker cannot be retroactively keyed. The worker package passed 31 unit tests and 19 integration tests, with one Python interop test ignored by default and three pre-existing host-cgroup observation tests excluded because the Docker cgroup path does not match the VM's systemd path. Warnings-denied Clippy and formatting passed. The updated 426-file source inventory test passed using the worktree index in the same pinned ARM64 container. The Python adapter and deterministic forwarding tests passed 94/94 under Root in a pinned Linux ARM Python 3.12 container and 93 passed/one Linux-only skipped on macOS. The separately invoked Python interop test passed in the pinned Root Linux ARM Python image: the Rust-generated sealed descriptor crossed an exec into the real Python adapter, which derived exactly the Rust worker's public key. These are isolated tests, not a Rust-controlled benchmark run.

An uninstalled Root-owned reader now requires caller-supplied hashes for both the keyed started marker and public-key sidecar, reopens the pair twice under the exclusive worker lease, and returns only the public identity with `execution_eligible: false`. An inert restart fixture accepted the same pair and refused wrong hashes and a substituted sidecar; a Root-only private-journal fixture accepted the exact pair and refused a wrong sidecar hash. These tests establish local pin comparison. They do not establish that the caller obtained either hash from a trusted host before the controller ran.

A keyed run now writes `hol-gauntlet-worker-terminal.v2`, binding the started-marker SHA-256, controller public key, and exact sidecar SHA-256 to the existing report, process and exit fields. The writer requires an expected sidecar digest and reads the sidecar before and after writing; the reader requires the matching keyed marker, v2 fields and unchanged sidecar after restart. A v1 marker and terminal refuse a later key sidecar. Because the v1 worker response cannot transmit an outside key pin, it projects a locally valid keyed terminal as `unknown`, never as `passed`. Two new keyed ARM64 unit tests and four existing terminal integration tests passed. The Docker-compatible worker selection passed 33 unit and 19 integration tests, with one ignored Python interop test; three pre-existing tests that sample the host systemd cgroup path failed in the Docker namespace and were excluded from that selection. Warnings-denied workspace Clippy passed. The terminal, keyed-test, lease and projection sources are SHA-256 `e7f1a93298abbb2e95fd9477c5ab51961c2fa9c9a0e21b9255806b7e916913eb`, `5b5918fe6bf92077bbe5fbb05855673a926410cc4cfb556da1b31d9bc5be5dbd`, `f6b2698ded037c25dcdc1f874507446773cebf01c2b92eaf4cbefa81012955c8` and `b04e6061a79b7e2904cf7563a3a44987aefa4c8e814dd580bab056607072eecc`, respectively. This terminal binding is local custody only; no outside host anchor or independent verdict has been established.

The complete outside-key exit remains open. No reviewed source-matched controller/private-cell install has run this new path on the VM. An [isolated host journal and terminal reader](gauntlet-rust-host-key-anchor-proof.md) can retain and compare these hashes, but no real prelaunch host/VM handoff has used them. The host must retain the v2 started-marker and sidecar hashes independently before controller execution, then refuse a changed marker or sidecar after crash/restart. Without those outside hashes, a Root replacement cannot be distinguished merely by rereading local files. The signed control records, SDK/Native peers, kernel observations and physical effects are not independently scored. The worker is unwired, all Rust observations remain `execution_eligible: false`, and the PR gate remains passive. The changed Python bytes yield controller tree digest `33c98333891743e6976bee9a123365fe7fe95dcf1bf9b65ee39a59fb41043c68` and 36-file private-cell source digest `909592fac5403f683df5673f5f195eac014986e91d50e547b7c214871507ae54`; the retained VM artifacts cannot qualify a fresh run until rebuilt and independently pinned. All three Rust controller-install-plan tests passed in the pinned ARM64 container with the independently recomputed Python tree digest.

At code pin `3645a8534c37016bd2dd7ba09b2129490d77d122`, the internal, still unwired Rust controller owner was connected to the six-control signed-opening reader. If a future fixed run returns a producer-claimed pass, it must read all six Root-owned controls, compare their report digest, and verify each signed opening and reported relation against the single job key that the worker generated before its prelaunch acknowledgement. The Python sealed-descriptor adapter deliberately forwards that one key to all six roles; distinct signed sessions and role bindings are still required. The owner takes no public key from a control record or report. An opening failure prevents the observation from being returned, but this is not independent effect scoring or a terminal verdict. The Rust package's v6/v7 config tests were also changed to embed their fixed fixtures, so the Linux test binary no longer depends on a macOS source path. The final SHA-matched ARM64 binary (`0831b00e70969dfdfd832fc562832cfe54a1253c2e8910326759c2368c942549`) passed 71 worker unit tests with three intentional ignores on the live VM. The native package tests and Linux ARM warnings-denied Clippy passed. These tests compile and exercise the component paths, but no live controller was dispatched through this new composition; immutable deployment, crash/restart host custody, independent SDK/kernel effects and model inference remain open.
