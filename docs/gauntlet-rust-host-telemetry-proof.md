# Passive Rust host resource proof

The pinned Python `ci/gauntlet/control_plane/telemetry.py` has SHA-256 `bc294a2507ef6adc1a86aa6086142ef4737ef939db8e7ad629c6d89d7d97c503`. `freeze_host_telemetry_v1.py` freezes its macOS host calculation with fixed `sysctl`, `vm_stat`, disk, CPU, load and time inputs. Rust matches the Python-frozen free plus inactive plus speculative page formula. It bounds and parses the two fixed macOS memory commands, samples disk with `statvfs`, CPU count and load from the host, and reports memory as unavailable if those commands fail. The direct `libc` 0.2.191 dependency was already present in the locked workspace; only the host crate's lockfile dependency list changed.

`gauntlet-host-shadow-host` is uninstalled and read-only. It first validates the private operations file's owner-only path, then emits a resource sample for the state volume. Two Rust unit tests cover the Python-frozen memory formula, malformed/duplicate page rows, and a positive native disk/CPU/load sample. The existing native ARM64 CI host-library test step includes them. No Rust observer lease, public snapshot write or admission is enabled.

On 2026-10-20, Rust and Python sampled the same Mac state volume about 3.4 seconds apart. Both reported `Darwin`, 32 CPUs, 549,755,813,888 bytes total memory, 3,996,329,328,640 bytes total disk, `online` and identical load at that moment. Free disk differed by 8,192 bytes and estimated available memory by about 270 MB because the host was active between samples. Those dynamic values must not be compared as exact byte vectors. A fresh collector still needs a durable sample timestamp, coherent snapshot publication and independent health/admission checks.
