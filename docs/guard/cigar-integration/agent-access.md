# Paired MCP context access

Context assistance is optional and off by default. The native service must verify the actual selected final CPython 3.14 process, CIGAR 0.14.1 package and approved worker before it accepts a context connection. Guard and its MCP server can continue using a different supported Python.

## Connect an app

1. In Protection, enable **Context for AI apps**, save preferences and start the verified runtime.
2. Under Workspace context access, choose the app as the **Context consumer**, choose the workspace and explicitly selected files, and approve the source grant. A dashboard grant cannot authorize an agent.
3. Configure the app to run the existing Guard MCP command, `hol-guard mcp serve --stdio`. Use `--guard-home` if selecting a separate Guard installation. This is a standard MCP stdio route; native app launch/extension qualification is reported separately.
4. Ask the app to call `get_context_status`. Match its public connection code in **AI app context connections**, select the workspace/app grant and approve the connection using Guard's existing proof flow.
5. Call `get_context_status` again to refresh discovery. The server advertises tool-list change notifications. The paired connection can use `get_guard_context` and `explain_guard_context` for its granted sources.

The current UI offers Codex, Claude Code and Cursor as permission targets. Pairing authenticates the MCP process that owns the private credential. The app label is the user's permission choice, not a claim that Guard has attested that app's executable or qualified every harness route. Current native status reports `identity_binding: human_paired_mcp_process` and `harness_route_qualification: not_established`. The actual generic MCP stdio protocol is tested; installed app routes remain required qualification work.

## Authority and privacy

The host generates a public connection code and a separate random 256-bit private credential. Only the authenticated native application IPC returns that credential to the MCP process. It is held privately in that process, and only its digest is retained in the native session table. No HTTP route creates a session or returns its credential. MCP tool arguments, prompts, argv, environment, browser payloads, operator lists, SDK context and diagnostics do not carry the credential. Debug formatting redacts it.

Only an existing proof-protected operator grant can bind a pending connection to an app/workspace scope. Reads and access-reduction routes cannot authorize. The native backend derives the scope from that authenticated session on every call; there are no caller-selected app, workspace, source, scope or runtime fields in context tools. Nested tool arguments are validated in Rust, including when FastMCP would otherwise convert or discard extra function arguments.

Each connection can explain only snapshots it prepared. A replacement connection cannot reuse the preceding connection's retained snapshots, even if the owner later gives it the same app scope. Current source, workspace policy, effective feature flags, runtime generation, lease and snapshot checks still apply. Context is supporting data and gives no command approval or execution confirmation. Logical scopes are not OS isolation between hostile processes running as the same user.

## Limits and recovery

There are at most eight pending/active native sessions. Pairing requests expire after five minutes. Approved sessions expire after one hour in ordinary graph mode or five minutes with separately enabled independent sharing, and are rechecked after context work. Ordinary graph mode permits one active connection per app scope. Shared mode permits independent paired connections and prepares their SDK clients during human pairing, refusing capacity before reporting authorization. The SDK's separate eight-client budget includes operator views and the optional private execution client. Scope and snapshot authority is memory only, including when evidence persistence is enabled. Turning off, reconfiguration, idle shutdown, explicit revoke/clear and runtime loss remove effective access; no connection credentials or authority are restored after restart.

Restart the MCP connection and pair its fresh code after an expired or lost authority. An uncertain session-creation response is not blindly retried. Explicit connection status polling does not keep an idle SDK runtime alive. Protection's connection metadata refresh does not drain SDK evidence or renew the idle timer. Revoke remains available independently of permission expansion.

Native context requests have a separate two-job limit in addition to the SDK actor's queue. Capacity exhaustion returns a bound `native_context_assistance_busy` refusal without scheduling the request. Context transport failures do not change the shared hook/approval health circuit. Stop and availability discovery remain independent of this context lane. Retry a refused read deliberately after checking status; do not assume that an interrupted mutation succeeded or repeat an unknown session-creation result.

The three general context tools and conditional `explain_guard_action` use one typed registry across direct calls, discovery and FastMCP registration. The action tool requires native policy/decision facts and resolves a recent authenticated native decision within the granted scope. See [native decision context](native-decision-context.md) for its limits and distinction from executable-byte validation. Discovery follows native availability. Cached calls still enter the backend and are refused when assistance is disabled, expired or revoked. The original six Guard MCP tools retain their handlers and behavior.

The FastMCP integration is verified against locked MCP Python SDK 1.30.0 and its [tagged official source](https://github.com/modelcontextprotocol/python-sdk/blob/v1.30.0/src/mcp/server/fastmcp/server.py). It overrides the public list/call handlers, advertises `tools.listChanged`, preserves the original tool arguments for native validation and uses text output explicitly for Guard's JSON text envelope. Earlier 1.28.1 observations used a development host below the declared dependency floor; the later locked environment satisfies all applicable Guard base requirements. This version-specific check does not qualify future SDK changes automatically.
