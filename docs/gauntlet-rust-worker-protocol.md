# Rust Gauntlet VM worker protocol boundary

This is the fixed request and response syntax for the proposed Root-owned Linux ARM worker. The implemented parsers are [`worker_request.rs`](../ci/gauntlet-rs/crates/gauntlet-contracts/src/worker_request.rs) and [`worker_response.rs`](../ci/gauntlet-rs/crates/gauntlet-contracts/src/worker_response.rs). They validate data only. An uninstalled [`gauntlet-vm-worker-shadow`](../ci/gauntlet-rs/crates/gauntlet-worker-state/src/bin/gauntlet-vm-worker-shadow.rs) binary can read the new private journal on Linux ARM64 with hash-only outside pins; it never executes a request. No Rust VM worker is installed or allowed to launch a candidate yet. The [execution checklist](gauntlet-rust-execution-checklist.md) tracks durable receipts, leases, process identity, conformance and cutover separately.

An additional uninstalled [`gauntlet-deployment-shadow`](../ci/gauntlet-rs/crates/gauntlet-worker-state/src/bin/gauntlet-deployment-shadow.rs) diagnostic accepts outside source, raw deployment-manifest and interpreter-target SHA-256 pins. It opens the fixed `/opt/hol-gauntlet/candidates/<source>` directory through Root-owned no-symlink descriptors, checks the manifest's exact fields and byte pin, then verifies the Root-owned config's canonical digest and source. It checks Root-owned controller and interpreter-parent ancestry, resolves only the fixed venv `python → /usr/bin/python3 → python3.<minor>` alias chain, and hashes the stable Root-owned executable target. The [retained VM proof](gauntlet-rust-worker-prelaunch-proof.md) returned the expected target digest and refused a wrong one. That target pin was observed on this VM for a read-only diagnostic; it is not yet an independently reviewed install anchor. The output explicitly leaves controller source, venv packages, binding the launched process to this binary, all assets and execution eligibility unverified. The fixed worker `inspect` response remains unavailable until those checks can support a truthful staged claim.

The separate uninstalled [`gauntlet-controller-shadow`](../ci/gauntlet-rs/crates/gauntlet-worker-state/src/bin/gauntlet-controller-shadow.rs) binds a complete Root-owned controller-tree inventory to the pinned deployment path and a third outside tree hash. Its [unprivileged ARM VM fixture proof](gauntlet-rust-controller-tree-proof.md) covers extra-file, symlink, hardlink and wrong-hash refusals. The retained controller installation still lacks a reviewed exact-tree digest, and this read-only diagnostic never grants execution eligibility.

The request is at most 1,024 bytes of bounded JSON. It has schema `hol-gauntlet-worker-request.v1` and exactly one of these shapes:

| Action | Required fields | Allowed effect |
| --- | --- | --- |
| `inspect` | `schema`, `action`, `source_sha`, `job_id` | Read a fixed Root-owned deployment declaration and report whether the exact source is staged. |
| `progress` | Same four fields | Read fixed progress/receipt paths without acquiring the active lease. Missing measurements are unavailable. |
| `reconcile` | Same four fields | Read the terminal receipt for the same job; missing or inconsistent evidence is unknown, never a replay instruction. |
| `run` | Those four fields plus `deployment_digest` | Attempt one source/deployment/job-bound execution only after Root-owned custody, lease and one-time started-marker checks. |

`source_sha` is 40 lowercase hexadecimal characters, `job_id` is 16, and the run-only `deployment_digest` is 64. Unknown fields, arbitrary command/path/profile selectors, duplicate JSON keys, missing pins and noncanonical identifiers fail before state access. The future host must obtain the deployment digest from an independent trusted channel. A digest carried in a candidate manifest or the request itself cannot pin the worker.

The `hol-gauntlet-worker-response.v1` syntax is limited to 2,048 bytes. Every response names the action, source SHA, job ID, worker-generation SHA-256 and one state. `inspect` admits `staged` or `unavailable`; `progress` admits `not-started`, `running`, `terminal`, `unknown` or `unavailable`; `reconcile` admits `terminal`, `unknown` or `unavailable`; `run` admits `running`, `terminal`, `unknown` or `unavailable`. `staged`, `running` and `terminal` carry a deployment SHA-256. `running` and `terminal` also carry the immutable started-marker SHA-256. `running` carries a kernel PID and process start tick. `terminal` carries a report SHA-256, exit code and bounded outcome (`passed`, `failed` or `invalid-evidence`). A `passed` outcome with a nonzero exit code is malformed.

The parser rejects unknown/misplaced fields, duplicate JSON keys, noncanonical identities and impossible action/state pairs. `bind_request` also compares the action, source and job to the original request, the worker generation to an independent pin, and any deployment digest to an independent pin. A missing terminal receipt is `unknown`; it never grants permission to retry. A parsed response is **not authenticated evidence**. The Root-owned worker must write an immutable, durable started marker before launching candidate execution, keep an exclusive lease, reject repeats after restart, and provide a signed or independently pinned terminal receipt. The host must authenticate the worker transport and separately verify marker/report bytes and process identity before trusting the state. None of those execution or custody rules is implemented by the parsers.

The inert `gauntlet-worker-state` crate supplies the one-time reservation primitive. For a parsed `run` request matching outside source and deployment pins, it creates `<job-id>.started.json` with exclusive creation and no symlink following, writes canonical `hol-gauntlet-worker-started.v1` bytes containing the job ID, source SHA, deployment digest and worker-generation digest, and fsyncs both the file and directory before returning the marker SHA-256. An existing started, running, report or terminal filename blocks another reservation; an incomplete or changed marker remains invalid evidence and must be surfaced as unknown. A Linux-only `<job-id>.running.json` marker can then bind the started hash to a pidfd-checked PID/start tick and cgroup, while the lease remains held. Read-only `progress` reports `running` only when the retained record and a fresh kernel sample agree; an absent, stale or changed running record is `unknown` after a start.

After a reserved run, the same crate can persist bounded canonical report bytes in `<job-id>.report.json`, then a canonical `hol-gauntlet-worker-terminal.v1` record in `<job-id>.terminal.json`. Both files are created exclusively and fsynced. The terminal record binds the outside source/deployment/generation pins, started-marker hash, report hash, PID/start tick, exit code and bounded status. A Root-owned live journal requires the terminal process identity to match the running marker. Restart reconciliation verifies the marker, terminal and report together. A report without terminal, a partial write, a changed report, or a symlink is unknown evidence and blocks replacement. A separate Linux-only `observe_process` primitive pins a live PID with pidfd and checks two `/proc` start-tick and unified-cgroup samples against outside expectations. `observe_process_resources` brackets bounded cgroup-v2 memory, peak, task, limit and event-counter reads with that identity check; missing or malformed counters are unavailable rather than zero. Their positive, mismatch and durable-running-projection cases passed as unprivileged static ARM64 tests inside the idle VM. The primitives still cannot authenticate the report, transport, exit outcome or cleanup. No Rust code launches candidate code.

`project_read_only` maps that durable state into the fixed response schema. It returns `not-started` only for a progress read with no marker; `reconcile` stays `unknown` without a terminal; a reserved job stays `unknown` for another `run` request; a verified terminal carries its exact marker/report digests. A `progress` read claims `running` only when the retained marker and a fresh pidfd/start-tick/cgroup sample agree. `inspect` and an unstarted `run` are `unavailable` in this passive implementation. It never launches a process.

`RunReservationJournal::open_root_owned` is the future live worker entrypoint. It requires Linux effective Root, no symlink in the absolute path, Root-owned non-writable directory ancestry and a final private directory with no group/world permissions. `acquire_active_lease` takes a nonblocking exclusive `flock` on a private `active.lock` file and keeps its descriptor alive through `reserve_under_lease` and `finish_under_lease`; replacing the visible lock file invalidates it. The current tests use the inert `open` entrypoint to test contention without Root. A live worker still must hold the lease through descendant cleanup, bind the pidfd/cgroup sample to its own launched process, and independently verify the terminal report and outcome.

The Linux-only `BoottimeDeadline` measures the active-run budget with `CLOCK_BOOTTIME`, which advances while the guest is suspended. It accepts only a trusted timeout of 1–86,400 seconds, refuses a backward clock sample and limits poll waits to 200 ms or the remaining budget. The existing Python host defaults to 3,600 seconds. This is a clock primitive only: no Rust dispatcher currently starts a child, kills its cgroup on expiry, reaps descendants or binds terminal status to the deadline.

Only a separately reviewed worker artifact may interpret the request. Candidate source is inert input to the unprivileged builder; the worker must never import a candidate as Root. The existing passive release observer and optional PR gate remain unchanged during this protocol work.

The separate [`worker_receipt.rs`](../ci/gauntlet-rs/crates/gauntlet-evidence/src/worker_receipt.rs) reader handles the **existing Python worker** terminal JSON shape for shadow comparison. It checks independently supplied source/job/deployment/config pins and exact report bytes, but it cannot authenticate where those bytes came from, establish Root ownership or recompute control outcomes. Its result is always `execution_eligible: false`; it is not a substitute for the new durable Rust receipt protocol.
