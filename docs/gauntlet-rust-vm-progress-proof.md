# Passive Rust VM progress proof

The pinned Python `Agent.worker(job, "progress", timeout=12)` source in `ci/gauntlet/control_plane/agent.py` has SHA-256 `04aed1ecf337746caed8fbd011c59926b47b37719add867628ac6b70a5309215`. `freeze_vm_progress_v1.py` intercepts its subprocess call and records the fixed Lima/`sudo -n`/Python worker argv, request and timeout for jobs with and without a deployment digest. Its fixture generator makes no VM call. `VmProgressPlan` reproduces these two plans and permits only the `progress` action with validated source/job/digest identities. It sends at most 1 KiB of request JSON, bounds stdout to 1 MiB and stderr to 1,500 bytes, and times out after 12 seconds. A malformed, duplicate-key or wrong-identity response is unavailable.

The uninstalled `gauntlet-host-shadow-progress` reads the existing private operations and job record through the host's bounded no-symlink readers, then invokes only this fixed read-only progress request. It emits a small summary; it does not publish the worker's raw JSON, take the Python observer lease, start or reconcile a job, or admit a build. Four Rust tests match both Python-frozen calls, exercise a fake Lima executable's stdin and failures, and refuse unsafe identities and malformed responses. The native ARM64 Rust CI job includes them.

On 2026-10-20 the Rust diagnostic and an independent Python `Agent.worker` call observed retained v3.48.0 job `7b3dd7131df5fedd` on the idle VM seconds apart. Both reported source `3864097f2e4fe623e403c1a948d9882f34c78690`, phase `diagnostic-passed`, six completed controls, no current control and `process_alive: false`. The timestamps differed. This is a producer-reported historical progress view; it does not independently verify the six controls, authenticate the installed controller, or establish a fresh Rust-controlled run. The Rust CLI labels process liveness as producer-reported and always returns `admission_eligible: false`.
