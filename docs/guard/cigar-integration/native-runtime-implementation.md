# Native runtime implementation

The `guard-context-assistance` crate verifies a selected runtime and controls a persistent public-SDK bridge. The native resident owns optional activation, recheck, status and stop operations, exposed through authenticated HTTP framing. Rust also owns scoped source/context operations, paired agent access, separately enabled sharing/persistence and optional execution context. The [execution log](EXECUTION_LOG.md) binds each capability to its tested artifact and limits. Ordinary synchronous hooks have no mandatory CIGAR dependency. [Local acceptance](ACCEPTANCE.md) records the completed authorized P0–P5 scope and the external/baseline qualifications that remain open.

Local [frozen onedir evidence](evidence/receipts.json) qualifies the actual frozen daemon, CLI and paired MCP with Guard Python 3.12.13 and a separately verified final Python 3.14.7 runtime. Later [onefile evidence for `486d6d9f`](evidence/receipts.json) also qualifies graceful zero-exit shutdown. The subsequent `d780af20` [onefile control failure](evidence/receipts.json) remains retained. Its correction at `1e341429` passes [all four matching frozen cases](evidence/receipts.json), including three fresh context profiles, strict Stop, zero-exit shutdown and zero descendants. A running Guard host is required; standalone short-lived CLI activation does not keep a native service alive. Full Desktop application and public release acceptance remain separate work.

## Implemented boundary

1. `RuntimeSelection` contains private, absolute interpreter, site-packages and working-directory paths. Launch retains the selected interpreter spelling, preserving virtual environment discovery.
2. `BundleApproval` describes independently approved installation bytes. `inspect_bundle` only inspects; it does not grant readiness. Explicit local candidate enrollment retains approval in the native private registry only after real process verification. HTTP/MCP callers cannot submit their own approval or replace this registry. Public installation and release qualification remain pending.
3. Before any launch, native code checks the interpreter digest and complete package inventory against the approval. The inventory includes bytecode, unexpected extra files, package metadata and the bundled worker. It rejects symlinks, startup-hook files, writable shared paths, mismatched release/protocol/platform metadata and oversized inventories. The working directory must be private on Unix.
4. A fixed `-I -S -B` interpreter probe runs without SDK imports, user site, `PYTHONPATH`, `.pth` processing or inherited environment. The observed process must be final CPython exactly 3.14, with the qualified build and platform/ABI combination. Caller-provided facts cannot create a `VerifiedRuntime`.
5. The bridge loads the explicitly verified package directory under the same isolated startup flags. It calls only public local SDK methods. It reads no selected workspace files and handles no approval keys or execution grants.
6. Native code requires a real worker handshake, matching capabilities and a synthetic compile plus snapshot verification. It rechecks package and interpreter bytes after initialization. Only then does it construct the non-deserializable runtime capability.
7. Private newline JSON IPC has 1 MiB request and 4 MiB response caps, bound request IDs, a serialized bounded queue and finite call deadlines. The Unix child owns a dedicated process group. Transport failures and unknown outcomes close the bridge/domain; mutations are not blindly retried. Windows activation remains unavailable until a persistent Job Object transport is implemented and qualified.

The expected receipt is an installation trust boundary, not an attestation from the selected executable. A checksum supplied by a browser, agent or arbitrary request is insufficient. The present development tests approve only the explicitly staged local candidate. Same-UID hostile-code isolation and public release signing are not established by this checkpoint.

## Persistent graph behavior

The native host can open bounded workspace graphs, atomically replace admitted sources, define narrow read-only views, compile cited context, request selection details, revoke views and close workspaces. Source/view/workspace counts, text sizes, context budgets and IPC are bounded. The native wrapper rejects required document IDs outside the view before sending them to the SDK.

Workspace and view handles are private native types. Reopening a workspace or replacing a view changes its generation. Old handles cannot access the new instance. Retained contexts contain exact readable-source revisions and full SDK context; the public brief is a separate data projection. Neither is an execution permission.

The brief validator checks the workspace/view, token budget, block/citation scope, admitted full text and line ranges. CIGAR uses the view's scope digest as the snapshot policy revision; the host policy revision is preserved separately in the retained request. Revisions remain strings. A readable-source change invalidates a retained context, including an unselected document. An update outside that view can preserve it. Selection details run on demand and revalidate with the worker.

`ContextDocument` means already-admitted host text. It does not authorize a file read or certify that arbitrary caller text is a native fact. Production adapters must derive facts from native admitted records and read explicitly selected documents through protected native source admission. No caller-controlled locator should be opened by the bridge.

## Resident control boundary

`context-assistance-enroll-local --stdin` is an explicit native operator command for an approved local candidate. It accepts schema `guard-cigar-enroll-local.v1`, verifies the candidate and stores a private, ID-bound record. It is not an HTTP/MCP enrollment endpoint. Listing returns only IDs, platform/version and worker identity. Enrollment and saved intent do not activate assistance. The first real settings opt-in verifies a registered selection's current bytes.

`context-assistance-control-v2` requires a home-pinned resident store. Native code loads local/workspace/managed settings, rejects public authority fields, and owns one cancellable background verification job. Results are accepted only for the current preference generation after reloading native settings. Stop closes active work before persisting opt-out. A watcher runs only while active to observe settings changes, a bounded private bridge heartbeat and idle shutdown. Status itself performs no SDK RPC, import or scan; the optional state's lock is separate from policy/evidence locks.

Existing daemon authentication protects `GET /v1/context-assistance`, explicit `GET /v1/context-assistance/installations`, and `POST /v1/context-assistance/{recheck,activate,stop}`. The request has no client-supplied executable or interpreter facts. Unavailable assistance is a bound operation error rather than an enforcement-policy error. There is no oneshot SDK fallback. [Sharing](broker-sharing.md) and [SQLite persistence](private-persistence.md) have separately enabled native implementations with their own grants, lifecycle checks and version-bound evidence; enabling local assistance alone enables neither.

Optional control framing starts its two-second RPC budget after separately bounded native preparation. Queue wait consumes that same RPC budget; it never resets before sending. Native readiness retains its existing five-second normal/twenty-second first-probe bounds, so total optional control wall time can include both phases. Hooks and workspace calls retain their original inclusive preparation budgets. No extra probe or mutation retry is added. The [cold-control source checks](evidence/receipts.json) follow a [frozen read-only reproduction](evidence/receipts.json) where readiness succeeds in 2,114.923 ms and the old framing sends no request. The matching frozen qualifier passes all four cases at `1e341429`; matching browser/backend and performance checks remain separate.

## Resident request scheduling

Potentially long workspace/source/connection operations and installation listing use a separate native lane with at most two admitted jobs per resident. At most two native workers start lazily and serve subsequent requests; each retires after one second idle. An unused lane starts no worker. This internal retirement is independent of the user setting for SDK/runtime idle shutdown. Slots cover queued work, evaluation and response delivery, so slow consumers cannot create an unbounded set of reply threads. Native code rechecks the existing accepted-request budget before evaluating a queued job. Failed spawns or worker loss refuse unevaluated work without replay. Closing admission wakes idle workers and includes their retirement in the existing bounded drain. The SDK actor queue and its deadlines remain independently bounded.

The authenticated frame digest is checked before scheduling. Scheduling tags are hints, with decoded escaped strings supported; complete strict native operation, home, scope and policy checks still precede context work. Status, stop, activation scheduling and agent discovery stay outside this lane. The reserved catalog metadata worker and existing continuation lane retain their original responsibilities.

A full lane produces a request-bound native context `busy` refusal, with no scheduled mutation, instead of a generic resident overload frame. Optional context transports also exclude their observations from the shared hook transport health circuit. Their Rust supervisor owns optional runtime health and cancellation; transport loss, malformed replies and busy results cannot open or reset the shared approval/hook circuit. Other native transports retain their existing health behavior. Reply binding, runtime eligibility, source/scope validation and refusal behavior remain mandatory.

Resident teardown closes admission to the context lane, permanently closes that resident's optional service and cancels verification, notifications and the SDK actor before bounded worker draining. This cleanup does not edit saved consent. A subsequent resident starts without any verified SDK runtime, source grant, connection credential or snapshot authority; saved opt-in alone cannot restore them.

Native framing tests hold two context responses open and verify bounded admission, canonical bound refusal, ordinary health and real stop availability, frame tampering refusal and slot release. Actual SDK control tests cover runtime retirement, pending cancellation, no late settings reactivation and preservation of saved intent. These tests establish scheduling and lifecycle properties, not measured production hook SLOs, total process memory or app harness qualification.

The Protection panel and public `context` CLI frame these controls; see [runtime controls](runtime-controls.md). State schema `guard-context-assistance-status.v2` separates validated local `preferences` and `requested_enabled` from `effective_preferences`, `restriction`, and native `verification_permitted`. A managed prohibition preserves the saved choice while refusing enrollment and verification before SDK I/O. All settings dimensions participate in generation invalidation. An unrelated settings save omits unchanged context preferences, and read-only native intent metadata cannot be written or exported as a machine reference.

The real CLI/resident/SDK process test passes outside the earlier restricted execution environment. An early installed checkpoint passes 85 selected CLI/settings/lifecycle/gate tests, superseding its earlier IPC failure while retaining that receipt. The package at `7714410b` passes actual browser source acceptance with a real daemon and SDK, including separate source proof, citations, stale/refreshed comparison, withdrawal/revocation and opt-out; see [the installed browser receipt](evidence/receipts.json). Later [installed backend acceptance at `d780af20`](evidence/receipts.json) covers 13 cases across approvals, native owner loss, Pi/OMP SDKs, persistence restart, MCP retrieval and concurrent clients. ## Native workspace runtime

`context-assistance-workspaces-v1` adds a separate optional graph actor. The actor owns the verified runtime and ephemeral workspace grants; its queue holds four jobs and each call has a six-second queue-plus-work deadline. Cancellation fences late results, and an uncertain outcome ends that actor generation. The settings watcher reads atomic actor liveness instead of calling the SDK under its mutex.

The native workspace API separates `workspace` (list/compile/explain), `workspace_access` (refresh/withdraw/revoke/clear), and `workspace_grant` (explicit operator admission). These map to authenticated `POST /v1/context-assistance/{workspace,workspace-access,workspace-grant}`. Only grants expand access and require the existing native settings approval proof. Thin HTTP framing strips that proof from the context payload. These routes are operator controls; a requested app name does not authenticate an agent.

Each grant binds a canonical native root identity, app target, effective workspace restrictions, selected relative file paths, source hashes and private graph/view handles. Native secure reads and secret scans finish before text reaches the SDK. Inputs are bounded to 32 files of 64 KiB each, with 4 KiB line-preserving chunks. Global off drops every grant. Workspace policy revocation closes the graph, clears retained documents/contexts and requires a fresh grant after recovery. Compile and explanation recheck readable sources and policy; old snapshots are refused after changes. The UI receives validated citations and plain-text excerpts as supporting data.

The general native policy document describes Guard's approval/context invariants. A particular pending action uses the separate [native decision context](native-decision-context.md) and [execution association](native-execution-context.md) boundaries. [Source/evidence notifications](source-evidence.md), [authenticated MCP callers](agent-access.md), sharing and persistence are implemented and retain their own evidence. A graph or policy excerpt alone never certifies a command or grants execution authority.

The early [native control receipt](evidence/receipts.json) records real candidate verification through the resident protocol and separately reproduces three unchanged hardened macOS launch-test failures. Subsequent installed HTTP, browser and frozen checks appear in the execution log with exact artifact boundaries. Full Desktop application, public packaging, Windows process ownership and the platform matrix remain outside those local macOS arm64 qualifications.
