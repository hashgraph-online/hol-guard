# Bounded recovery of an initial CIGAR selection

An explicit recover request for an initial selection can now verify an already committed target before completing its records. It uses the existing native switch worker, profile lease and 32-job namespace. It requires the current native generation; the original selection request and its generation remain unchanged.

Admission authenticates the initial marker, requires exact target preferences with both enablement values false, and reconstructs the profile-bound native empty-data proof. Existing app data, changed settings/policy, a different selection or a replaced profile refuse recovery. The worker resolves current catalog/update rules, starts only a temporary target, performs the normal requested SDK checks, rechecks artifact/transport identity, and measures the exact sealed target. It closes the target before the short record-reconciliation lane. No preferences, native generation, app/file/note grants or serving actor are restored.

Each explicit attempt has a fresh random ID, current native generation, start time and fixed 120-second deadline. The original job/request fingerprint and original preparation deadline are immutable. Progress is not verification or authority. A live same-generation retry returns the same native attempt. After cancellation or a fresh Service, another explicit recover may create a new attempt only after admission succeeds again.

Cancel markers retain the old shape for ordinary jobs. Recovery markers additionally bind the exact attempt ID. The current marker cancels that attempt; a valid old marker does not cancel a later explicitly requested attempt. Stale progress cannot change the live attempt or extend its budget. Malformed or mismatched parent-request markers refuse. No cancellation file is deleted and no old SDK client, scope, ticket or Guard approval is reused.

The initial marker continues to gate activation until the target record is reconciled and Healthy/Completed are acknowledged. An unknown record-write acknowledgement leaves recovery pending; a later attempt observes and verifies the target rather than rewriting preferences or replaying SDK mutations. Existing Healthy completion acknowledgement remains metadata-only and starts no SDK. Recovery failure or cancellation leaves the selected profile disabled and retains its data/intent for another explicit attempt.
