# Rust worker prelaunch checks on retained Linux ARM VM

On 2026-10-20, the idle 16-GiB `hol-beta-bootstrap-20261016-004` VM retained the v7 deployment for source `b4efd8171b06d0e13cbe12a077c376ecdc891fd1`. The read-only deployment manifest had raw SHA-256 `e65ab14fb8cb3d4ecb5f5eec3ff96170b2d6efd24c51e5a14d428e4427011e36`. The VM's `/usr/bin/python3.12` binary had SHA-256 `c86f21d0da9290ece2d7d49a3f7ed52aed59cb029abdf0ea25c79634f6cbe960`. This latter hash was observed on the same VM and supplied as an outside *argument* to exercise the diagnostic; it is not an independently reviewed software-supply pin.

The Rust 1.88 static ARM64 `gauntlet-deployment-shadow` binary had SHA-256 `753f4c00578635ef3773e42f21cafc2537360f2556abdafdc5a0bad3a395e40a` both locally and at `/home/construct.guest/gauntlet-deployment-interpreter-753f4c00`. It checked the source-bound deployment declaration, canonical config digest, Root-owned no-symlink ancestry and the exact venv-to-system interpreter alias chain. The positive invocation returned `interpreter_target_path: /usr/bin/python3.12`, the expected binary hash and `interpreter_target_verified: true`; it also returned `controller_files_verified: false`, `interpreter_execution_bound: false` and `execution_eligible: false`. The same invocation with a 64-zero interpreter hash exited 2 with `deployment declaration differs from its outside pins`.

The same source cross-built the `gauntlet-worker-state` static test binary with SHA-256 `d7fe0bfbf3159aea5062c4cfcc34fac47cd909060587f43d8219e7b655350d37`, which matched its guest copy. All 15 unprivileged ARM VM unit tests passed, including the `CLOCK_BOOTTIME` deadline boundary, clock-regression refusal, fixed alias parser, pidfd/cgroup observation and durable state tests. The deadline is a local active-run clock primitive; it has no process-launch or termination effect.

The read-only `observe_cgroup_drain` primitive now samples a retained cgroup-v2 subtree twice through no-symlink descriptors. It requires both `cgroup.events` `populated` fields and both hierarchical `pids.current` values to be zero, an empty direct `cgroup.procs` file, and the same cgroup inode on reopening. Missing or oversized files, malformed counters and replaced cgroups are unavailable rather than clean. The [Linux kernel documentation](https://cdn.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html) defines `populated` over a cgroup's descendants, which is needed to detect surviving grandchildren. Synthetic cases cover conflicting counters and invalid values. A new static ARM64 test binary had SHA-256 `2d437aa0d2a0bb7a0a350b7fec26f746abd21205f13349f2eccd52f448a5a615` on host and VM; all 15 tests passed unprivileged, and the live test observed its own occupied cgroup as populated. No empty live product cgroup was created or certified. A future terminal writer must retain exclusive ownership and prevent new entries while using this observation; this snapshot alone cannot prove final cleanup.

No benchmark or model ran, no Root worker was installed and no existing Python journal was touched. The retained controller source is still [not an exact reviewed generation](gauntlet-rust-controller-source-audit.md). Before a Rust `run` can be eligible, the launcher must verify and bind an independently pinned controller and interpreter to the actual child, enforce the deadline and descendant cleanup, authenticate report outcomes and pass a fresh exact-commit conformance run.
