# Candidate-bound local-model handoff proof

The active Python host already passed a Git candidate SHA to provider startup, but the provider's retained startup manifest did not carry that SHA. A copied manifest could therefore be prepared for a different candidate without the VM comparing the provider's candidate to its request. This change puts `candidate_source_sha`, `job_id` and `profile` into the private authorization, provider binding and signed startup record. The signed record also carries the canonical binding-file SHA-256. The VM's `inputs` reader now requires those three identities to equal its exact prepare request, recomputes the binding digest, and requires the retained provider quota status to name the same digest. The existing outside transfer-byte SHA-256 checks and Ed25519 signature check still run first.

The reviewed source map pins `live_provider.py` SHA-256 `650b1964a1aba988ccd239f13a933ea0697d9b169656f72a86999d5b015a25db` and `vm_live.py` SHA-256 `54e75a012721ce388b27e841f715c58c3b3281a94056570b6728d2aea134e474`. The Python preflight and startup fixture generators were refreshed against the former file; their selected admission and return AST hashes remain unchanged. The 427-file integration map has 52 changed and seven added controller files relative to the pinned baseline; the later host-only dashboard command does not change this provider proof.

`verify_live_provider_manifest_claim` in the Rust host crate reads caller-supplied, outside-SHA-pinned manifest bytes without starting a provider. It checks the self-declared Ed25519 signature, job/profile/source, binding hash, settled quota counters, known-token observation and loaded-model relation. It always returns `producer_claim_only: true` and `execution_eligible: false`. The manifest's public key is generated by the provider itself, so its signature proves internal consistency only; it does not establish independently reviewed provider provenance or authorize model-token spending.
