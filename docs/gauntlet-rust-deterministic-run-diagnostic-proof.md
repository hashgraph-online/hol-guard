# Rust deterministic controller diagnostic: dispatch boundary

The new opt-in `gauntlet-deterministic-run-diagnostic` binary reads one bounded canonical `run` request, verifies its own Root-owned installed ELF against an outside SHA-256, holds the exclusive Rust worker lease, and composes the Root-owned deployment, controller-tree, interpreter, v7 config and all inert asset checks. The existing controller owner then creates the capped job cgroup, refuses stale job output before reservation, reserves a one-use keyed marker, sends its prepared frame to the host, and waits for a durable host acknowledgement before descriptor-bound controller execution. It observes the child, enforces a `CLOCK_BOOTTIME` deadline, kills and drains descendants, stops the exact product-cell slice, rechecks all pinned inputs, and opens the deterministic report and six signed records when the producer claims a pass. Only after those checks does the new entrypoint write a keyed terminal with status `invalid-evidence`. The persisted Rust report distinguishes the controller's status claim from an independent verdict and sets `execution_eligible:false`.

The paired `gauntlet-host-deterministic-run-diagnostic` invokes only the compiled Lima VM and digest-named guest binaries. It fsyncs the one-use public-key pin before acknowledging the worker, bounds the guest's final JSON output to 4096 bytes, and matches the job, source, started marker, key sidecar and public key to its durable record. After the guest exits, a separate Root-only `gauntlet-deterministic-readback` binary verifies its own ELF, reopens the keyed terminal and canonical diagnostic summary, checks the fixed deterministic controller report digest and product-slice absence twice, and emits a bounded response. The host reopens its retained pin, calls the fixed Lima readback command with a 16-KiB output and 60-second cap, recomputes the terminal and summary hashes, and binds them to the original key and the completed guest's claimed hashes. It still does not independently score Guard controls, attest the VM or mark a PR eligible.

Host transfers and separately installed Root-owned digest-named paths matched both hashes; each ELF was mode 0500 and single-link. A SHA-matched ARM64 worker test binary `4499718cc39499305ca3deba674447cac170f388fac00a3ce5291ba40ab14a01` ran on the 2-vCPU, 16-GiB VM: 101 tests passed, zero failed, 20 Root/fixture cases intentionally ignored. The same suite in a Docker cgroup namespace had four expected live-cgroup-path failures (97 passed) before the readback change; the VM run supplies the relevant kernel layout. The macOS host library tests passed; the targeted host sets passed one final-result parser, six process and three keyed-readback cases, including a fixed-argv fake-Lima call and changed key, status, report and replay refusals. ARM64 release builds, Mac/ARM64 targeted checks and warnings-denied Mac host Clippy passed. The readback ELF separately refused an absent job marker and an incorrect own-binary digest with exit 2. These are installed-command negative proofs; no one-use job was consumed.

A read-only inventory of all 21 existing candidate deployment manifests found no controller generation containing the sealed-key adapter `HOL_GAUNTLET_RUST_SIGNING_KEY_FD`; the separately installed newer adapter-enabled controller generation is not named by any of those immutable deployments. Launching one of the existing deployments would knowingly produce a key mismatch and consume a one-use job, so no live controller run or positive readback was attempted. The next execution step needs a fresh source-bound deployment that names a reviewed adapter-enabled controller, then a host-pinned run and terminal readback on the same job. Six-control verdict recomputation, product-internal effect attribution, controller/VM provenance and model inference remain open. The Python observer and passive PR gate retain authority.
