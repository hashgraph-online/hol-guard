# CIGAR locked-wheel preparation

Status: native preparation and source-build runtime checks are implemented. The offline background installer and authenticated managed-slot publication now have real source-build evidence in [Native installation jobs](CIGAR_INSTALL_JOBS.md). [Exact public acquisition](CIGAR_ACQUISITION.md) also has native source-build evidence; [private Python preparation](CIGAR_PRIVATE_PYTHON_PREPARATION.md) now has native real-artifact evidence, while durable setup, runtime switch/rollback and Versions & updates UI remain in progress. This document does not describe a delivered end-user updater.

The native owner uses `guard-cigar-release` to resolve authenticated exact metadata and `guard-cigar-install` to prepare the selected wheels. The installer has no network client, dependency resolver, pip, ensurepip, source builds or Python package imports. Acquisition is a separate native-owned boundary; a browser cannot supply these local paths or change the lock.

## Preparation contract

`prepare_locked` accepts a resolved release, the exact SDK/dependency wheel paths keyed by locked filename, and cancellation/deadline control. It rejects extra or missing wheels and verifies their complete hashes and byte lengths before ZIP parsing. ZIP parsing uses pinned `zip` 9.1.2 with Stored/Deflate support only. Its Rust minimum is 1.88; the project retains its declared Rust 1.88 minimum.

Limits are 128 MiB per input/member, 256 MiB combined compressed and expanded bytes, 8,192 output files, 24 path components and a 120-second maximum preparation control. The bounded single-disk, non-ZIP64 directory envelope is checked before the ZIP library allocates its index. Encrypted archives, overlapping entries, CRC failures, symlinks, device/special files, traversal, duplicate/case-alias paths, import hooks and unsupported `.data` relocation layouts refuse. Filenames use a deliberately narrow portable subset; an unsupported layout needs a reviewed installer change and qualification.

The complete deterministic tree hash must match the catalog before any output is written. It uses the existing `guard-cigar-package-tree.v1` algorithm, including exact SDK and dependency files. `BundlePlan::write_into` requires a fresh canonical owner-private directory, creates files exclusively, preserves only executable/nonexecutable intent, writes protected file modes and checks cancellation between chunks. A failure leaves private staging for its native job owner to reconcile; this low-level API neither publishes an installation record nor changes the selected runtime.

`slot_id` v2 binds release/profile identity, immutable platform/artifact/dependency/tree/worker facts and the independently verified Python executable digest. A changed build or interpreter receives another slot. Catalog checkpoint, download origin, qualification/features and qualification receipt refreshes are excluded. An installed record still requires actual protected-artifact, interpreter and doctor checks plus the owner-authenticated registry receipt.

## Maintainer workflow

`scripts/cigar_catalog_entry.py` drafts one exact release entry from an independently approved upstream release manifest, SDK wheel and complete dependency wheel set. It verifies SDK bytes against the manifest, checks dependency requirements for the target final CPython 3.14 environment, preserves actual SDK/dependency Requires-Python headers, computes the installed tree and records independent SDK/core/source/manifest/worker identities. Native [interpreter compatibility](CIGAR_PYTHON_COMPATIBILITY.md) checks those constraints before job/download and after the actual probe; the wheel preparer binds declared requirements to exact metadata. It imports no SDK and installs nothing. It currently drafts macOS arm64 only; other platforms require their own real artifacts and qualification.

The script takes `--sdk-wheel`, repeated `--dependency-wheel`, `--release-manifest`, `--platform`, `--build-id`, the exact final `--python-version` being qualified, and a new `--output` file. Optional repeated `--dependency-url FILENAME=URL` values record exact content-addressed files.pythonhosted.org origins for supplied dependency wheels; omitted origins remain offline inputs. The Python patch is an input rather than a code pin; dependency markers use that target version independently of the maintainer's host Python. It emits upstream-only draft data with no Guard qualification or enabled features. It does not edit a catalog, trust an arbitrary manifest signature, promote a release or change catalog signing keys.

Review the draft against upstream provenance and the shipped adapter. Add the exact data to the Guard-bundled catalog or its separately authorized signed publication workflow. The native preparer then verifies those bytes again. A compatible SDK addition changes catalog/locks/qualification data; breaking Python, SDK API, worker/broker protocol or storage behavior needs an explicitly shipped adapter/Guard change.

The `guard-cigar-install` maintainer example `qualify` takes `BUILD_ID PYTHON FRESH_PRIVATE_HOME SDK_WHEEL DEPENDENCY_WHEEL [...]`. It resolves bundled metadata, extracts the exact pinned tree, inspects the result and runs graph, sharing, persistence and execution-handoff checks on synthetic data. It saves a stopped-runtime receipt and never enrolls, selects or enables CIGAR. It currently targets macOS arm64. Its receipt proves source-build feature behavior, not the installer transaction, runtime switch, signed Guard distribution or frozen application.
