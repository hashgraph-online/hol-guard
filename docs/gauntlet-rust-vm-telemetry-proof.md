# Passive Rust VM telemetry proof

The pinned Python `ci/gauntlet/control_plane/telemetry.py` has SHA-256 `bc294a2507ef6adc1a86aa6086142ef4737ef939db8e7ad629c6d89d7d97c503`. `freeze_telemetry_v1.py` stores its exact fixed Lima/Python VM probe command, one accepted response, an unavailable response and 11 resource-admission decisions. The uninstalled Rust `gauntlet-host-shadow-vm` reads the existing owner-only operations config, invokes the same fixed read-only VM probe with no shell or stdin, bounds stdout/stderr and time, and strictly validates the returned metrics. It never takes the observer lease, changes a VM file or admits a job. Probe errors and malformed measurements remain unavailable; the pure admission reducer checks staleness against a caller-supplied time.

Four Rust tests match the Python command and all 11 reason lists, reject duplicate/missing/implausible metrics and unsafe configuration, and exercise a fake Lima executable's success/failure. The isolated native ARM64 CI job includes these tests. The preexisting tag lookup now shares the bounded fixed-process helper, and its tests still pass.

On 2026-10-20 Rust and Python independently probed `hol-beta-bootstrap-20261016-004` seconds apart. Both reported `running`, two CPUs, 16,733,863,936 bytes guest memory, 48,803,864,576 bytes guest disk and 8,669,839,360 bytes free disk; the memory-available value was also identical at 16,143,572,992 bytes. That free disk is only 79,904,768 bytes above the configured 8-GiB admission floor. A new source build could cross the floor, so this proof does not start one. The metric timestamps necessarily differed.

This is a VM connection and resource-observation proof, not a complete host observer or a durable dashboard collector. The configured `limactl` binary and VM process were not independently attested; no lease, progress, receipt, provider or source eligibility was established. The Python release observer remains authoritative, and the Rust probe always reports `admission_eligible: false`.
