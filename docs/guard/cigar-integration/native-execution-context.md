## User controls and supported route

The advanced **Associate native context with execution** preference is independently off by default. It requires the global CIGAR opt-in, an explicitly verified final CPython 3.14 runtime and approved CIGAR 0.14.1 package/worker, enabled native policy facts and a fresh app/workspace grant. A separate selected 3.14 environment works while Guard itself uses an older supported Python. Saving a preference alone does not start a runtime or grant access.

The first adapter covers Guard's native captured-Bash route on macOS for Pi and Oh My Pi. Source capture still needs to satisfy that route's existing proof profile. It does not install an app adapter, qualify external app delivery, enable a new MCP execution tool or change which commands Guard can execute. Codex, Claude Code and Cursor retain their separate scoped MCP context controls; this setting does not claim a new execution adapter for them. Windows and other owning executors require independent implementation and qualification.

Execution context does not require **Context for AI apps**, agent sharing or saved evidence. Workspace access offers Pi and Oh My Pi as native executor consumers when this feature is selected. MCP consumers and connection pairing retain their own permission gate. Managed/workspace policy can narrow execution preferences and source permissions; it cannot create local consent. Turning the feature or global assistance off invalidates the old runtime generation and grants.

## Execution flow

1. Guard captures the actual source/image and its subject, obtains the existing artifact hash and evaluates current policy under its native fence. With assistance off, the existing execution path continues. Very short remaining native deadlines skip the optional stage.
2. For an eligible opted-in request, native code derives a private semantic commitment from the existing tool-intent digest, captured subject, artifact hash and admitted policy identity. It mints an opaque effect ID. Commands, environment values and private capture descriptors are excluded from SDK documents and public observations.
3. Guard retains the captured bytes but releases its policy/control fence before reading current assistance settings or waiting for the optional actor. No approval has been spent. The actor must match a current native app/workspace grant.
4. A dedicated private memory broker supplies a fixed native-facts document. The scoped SDK client submits that exact draft. Rust verifies the complete stored submission, creates the independent native host review, checks it, binds the SDK precondition and takes the opaque handle once. Agent-written claims cannot review themselves through this path.
5. The optional actor wait is bounded to 100 ms including queue time. Expiry before dispatch atomically abandons the queued closure. An already dispatched timeout has an unknown SDK mutation outcome and closes that optional generation; the handle is not retried. Native execution continues through its own authorization path. Up to 100 ms of optional wait is added back to the command's native allowance, within the existing transport headroom; this is not a measured whole-request latency guarantee.
6. Guard reacquires its native policy/control fence. It checks the captured artifact and policy again, repeating native policy assessment if the admitted policy identity changed. A stale optional association is dropped. The native journal allocates the actual physical invocation, including the existing logical-operation/tool-call alias behavior; native code associates the SDK effect with that allocated invocation.
7. Existing Guard authorization still decides whether the action runs. Both Allow once and Always allow retain their native claim/reuse rules. At the real launch barrier, the association polls native service/scope epoch fences, SDK-runtime liveness and its 30-second monotonic lifetime. It makes no SDK call, actor wait or source-content read there. The held value contains atomic liveness observations rather than an actor owner whose destruction could wait for cleanup.
8. Native dispatch acknowledgement, completion and uncertainty continue through the existing journal. Optional observation metadata follows those actual native events. Existing mandatory executor request/result schemas and approval payloads are unchanged. Reconciliation and retries use Guard's actual operation record, never a CIGAR ticket or snapshot.

The SDK's take establishes its check boundary; it neither sends a command nor holds an atomic lock across a later send. Observation metadata explicitly reports `approval_grant:false` and `send_boundary_atomicity:false`. An SDK precondition can succeed while the native executor refuses changed script bytes under an old saved approval.

## Source qualification

This execution view contains only fixed facts from the actual native capture and admitted policy. It contains no selected workspace documents, shared notes, receipt stream or other client's data. Its broker/view is separate from operator and agent retrieval, so parallel execution preparation does not replace their shared `guard:action` source.

Workspace documents and reviewed notes remain useful in independently timestamped review briefs and scoped context tools. They are excluded from a claim that their mutable bytes remain current at the native launch barrier. The [source-currentness investigation](execution-handoff-design.md#mutable-source-currentness-investigation) demonstrated an actual unflushed shared-memory-map write without a vnode event or metadata change. The proposed watcher was removed. Quiet notifications cannot replace protected content ownership or a read at the claimed boundary.

## Resource bounds and history

Expensive artifact checks, SDK qualification and private client setup run during explicit background activation. Command dispatch uses a prewarmed client. Its five-minute SDK lease renews on the optional maintenance lane; unavailability drops the association rather than creating a cold client in the command path.

An additional installed test waits **310 real seconds** after its first associated execution, observing status only, and then completes another captured Bash effect with a fresh completed context association in the same native generation. It preserves the saved Always allow and runs the original replay/restart/Stop checks afterward. **One case passes in 363.788 seconds**, zero skips/errors/failures, against `83d62bf7`. [Late-lease evidence](evidence/late-execution-lease-verification.json) binds its report, source and product identities. This proves late renewal at the installed macOS/OMP owning sink; a five-minute interactive external application and ambiguous in-flight effect recovery remain separate qualifications.

There is at most **one additional private execution broker domain** per verified runtime. It is separate from the configured workspace-domain count and consumes one slot from the unchanged global **eight SDK-client** budget. Operator views and paired agents use that same client budget. Token requests are intersected with current workspace limits and the activated domain's limits. No execution ticket, pending authority or native execution association is stored in the optional SQLite evidence cache.

Protection settings show preparation readiness separately from the SDK check and expose up to **32 recent metadata observations for five minutes**, in native memory only. The panel distinguishes prepared, no new dispatch, actual dispatch acknowledgement, native completion record and unknown outcome. It omits commands, queries, environment values, SDK tickets, submissions and semantic intent digests. The execution reference is SHA-256 of the fixed native JSON tuple `[physical_operation_id, artifact_hash]`; the SDK never chooses that invocation.

The observation list is bounded and may omit updates under contention. It is not the durable activity journal. Stop/reconfiguration closes the old list. Scope refresh, withdrawal and revocation remove its observations, and epoch checks under the observation lock prevent late completion from resurrecting revoked data. Explicit history removal also replaces the old observation owner. An unknown outcome directs the operator to Guard's native execution record before retrying.
