# Fixed Rust worker launch-plan parity

The pinned Python `vm_worker.py` launches its deterministic `ci check` with a fixed isolated Python invocation, Root-controlled controller and config paths, `/opt` asset root, `/home/hg-<job>` state root, `/var/lib/hol-gauntlet/outputs/<job>` output directory and a three-field environment. Its request cannot select a command, profile or path. The [fixture generator](../ci/gauntlet-rs/proofs/freeze_worker_launch_v1.py) checks SHA-256 `fb95cd33bf04c3e68c641972dc6bd5340a8cd87b1ad2948ba131c4a71c60aa9e` for that exact Python file, interprets only the fixed launch-list expression with bounded known values and never imports or spawns the worker.

The committed [two-case fixture](../ci/gauntlet-rs/crates/gauntlet-worker-state/tests/python_worker_launch_v1.json) reproduces with SHA-256 `0ac7b1c12cbb521ed7a5f3d3c7707c1a1a948aa35981b58445a661fd6bf1e009`. Rust's `fixed_launch_plan` matches every argv element, cwd, environment, state root, output directory and log path. It refuses mismatched request/deployment/interpreter pins, unsafe controller/interpreter paths and an injected command field. Its output explicitly reports `execution_eligible: false`.

A static ARM64 integration-test binary had SHA-256 `6b91db5cafeaa268496f77aa06b7b654e280876001b8969a63f495e3ff5ef2f5` on both host and the idle 16-GiB VM. Both tests passed unprivileged there. This is command-data parity only. A live worker still needs a reviewed Root-owned controller install, descriptor-bound interpreter execution, exact source/build custody, exclusive job lease, cgroup ownership, child reaping at the deadline, independent report scoring and interruption recovery before using any plan to spawn a process.
