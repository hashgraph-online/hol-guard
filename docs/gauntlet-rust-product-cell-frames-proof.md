# Product-cell frame dialect parity

Code pin `1ae40a54` extends the Rust `FrameCodec` with the Python
`product_cell_protocol.CellCodec` schema, HMAC domain and
`cell-supervisor`/`cell-actor` roles. It keeps that dialect distinct from
the VM controller/collector bridge while sharing the existing bounded
sequence, frame-size, aggregate-budget and poison-on-error implementation.

The frozen fixture was generated by the pinned Python
`product_cell_protocol.py` at SHA-256
`3813d609e3b08f949747810c6fec46db5797a113d20fb87ac2f8c5654bdc021c`
and `vm_bridge_frames.py` at
`f2d731788c2c82f4882a37ca4c9336b55aef80cd5d27a5e051af42a60c68460e`.
Rust matched all three exact Python frame byte strings and both directions'
decoded bodies on macOS and an offline Linux ARM64 Rust 1.88 container. A
cell frame with the same synthetic key was refused and poisoned by a VM
codec. Two real Python/Rust management-socket tests on macOS also exchanged
RPCs in both product-cell directions. Rustfmt, focused warnings-denied
Clippy, and the fixture generator's Ruff check passed. The offline ARM64
container lacked Python; the isolated ARM64 CI job now runs the live
interop tests with the Python environment.

This proves frame and RPC transport compatibility only. It does not read or
authenticate the private bootstrap, own the PID-1 actor, bind product
processes to a cgroup, reconcile Native effects, or grant a benchmark
verdict. The synthetic test key is public fixture data.
