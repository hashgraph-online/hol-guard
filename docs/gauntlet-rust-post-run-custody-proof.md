# Rust post-run input custody boundary

`PreparedLaunch::recheck_all_assets_after_cleanup` reopens the pinned Root-owned controller tree and checks its whole-tree digest, then rechecks the held interpreter inode and bytes. It reloads the exact source-named v7 config against the outside digest, repeats the inert inventory of every declared role, requires the original role count, and checks the controller tree and interpreter a second time. `run_prepared_controller_ineligible` calls this only after recursively killing/draining the controller cgroup, reaping the direct child, stopping and observing absence of the exact product-cell slice, and re-verifying the worker lease. A refusal leaves the started job unresolved; it cannot produce a successful terminal receipt.

Validation on 2026-10-20: native ARM64 `cargo fmt --all --check` and `cargo clippy -p gauntlet-worker-state --all-targets --locked -- -D warnings` passed in the pinned Rust 1.88.0 container. The rebuilt test executable had SHA-256 `f58e63048c1dfbefe14f35bfe26a7acc8360da44a0a66a46eb6995834eab8a4c` on the host and on the retained 2-vCPU/16-GiB VM `hol-beta-bootstrap-20261016-004`; its unprivileged run passed all 29 worker-state unit tests. Three of those tests fail in Docker because that container exposes cgroup `/`; they passed in the VM's real cgroup hierarchy. The post-run method was compiled but has not been exercised against a Rust-launched controller, so this evidence is a guardrail proof rather than a positive benchmark run.

The outside source and installer pins are still candidate PR values, and the readers are point-in-time checks rather than a complete concurrent-mutation proof. This does not authenticate a produced report, recompute any of the six controls, deliver a terminal receipt, or authorize a PR gate. The Python worker remains authoritative and the Rust worker parent exit stays open.
