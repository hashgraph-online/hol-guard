# Root controller launch boundary on Linux ARM64

The Rust worker now has a job-ID-derived `OwnedJobCgroup` with fixed controls: `memory.max=4294967296`, `pids.max=256`, and `cpu.max=100000 100000`. Its creation uses an exclusive cgroup name and verifies each control by reading it back. The internal `spawn_prepared_controller` path accepts only a `PreparedLaunch` whose Root-owned controller tree and held Python interpreter are rechecked around launch. It requires the exclusive worker lease and writes the durable one-time started marker before the child can execute. It creates only the fixed job log under the private Root-owned output directory, joins the controller cgroup in the child, sets a new session and `NoNewPrivs`, and calls `execveat(AT_EMPTY_PATH)` on the held interpreter descriptor with the fixed 22-argument deterministic command. This function is **not exported** from the crate while no dispatcher owns the child lifecycle. No production controller call was made in this proof.

The uninstalled `gauntlet-root-controller-exec-probe` exercises the same low-level Root descriptor-exec path with a fixed inert `-I -S -B -c` Python snippet that forks once. It does not import controller code, use the private-cell SDK, run HOL Guard, call a model, or produce a benchmark report. It observes the Root child identity, `NoNewPrivs: 1`, two tasks in the exact cgroup, then writes `cgroup.kill`, boundedly reaps, verifies recursive drain, removes the cgroup and rechecks the executable. This Root diagnostic does not clear Linux capabilities; the controller's privileged role still requires reviewed source custody and a complete worker lifecycle.
