# Native command corpus contract

The 51,000-case command corpus now exercises the production native evaluator and the host's effect composition using the evaluator's original, request-bound evidence. It is an offline diagnostic: it neither executes the target commands nor produces authenticated execution receipts. Its contract is recorded in `tests/fixtures/guard-command-corpus/native-contract.json` and checked by `tests/guard_command_corpus_native_contract.py`.

The original corpus generator, independent Python-era oracle, seed manifest and resolved `known-gaps.json` remain unchanged. The baseline decision-diff runner called Python `evaluate_command` directly, without native evidence; its Git blob is `d86da384c604ee349829b3dbebe7a115723a7b5a`. That oracle describes desired effect and approval behavior; it does not establish that the native parser and compatibility classifiers support every input shape. The [declarative authoring ADR](declarative-authoring-adr.md) requires preserving existing compatibility uncertainty and excludes general parser expansion from the authoring migration. Native parser uncertainty, unsupported compatibility context and evaluator errors must retain their restrictive native outcome. A diagnostic must not discard an error or create successful observations to meet the older oracle.

The separate native contract states an expected outcome for each of the 52 input sources. Sources with wrapper or pipeline variants use explicit selectors over the frozen input variants. Each group records its exact case count and a digest of its sorted, length-framed case IDs. Expectations include the final decision floor, raw native floor and reason, parser confidence and uncertainty reason, evaluator error, and uncertain rule IDs. They are authored input-side expectations, not values selected from the evaluator's observed decisions. Unlisted sources, changed membership, a different error or uncertainty signature, and any lower or higher unexpected decision fail the native contract.

The inherited source baseline is main commit `f674f69665cfbcb79ab9e82d671e99f7674905ae`. The fixture records baseline Git blob identities and current source SHA-256 identities. GitHub classifiers, ASCII comparison and the option parser are byte-identical to that baseline. The candidate incorporates upstream commit `5a076ded9182f4466b875effffae3b156fba9e04`, which adds bounded `2>&1` parsing and the exact `cd ... && find src -name '*.py' -exec python -m py_compile {} +` form, together with the corresponding domain-classifier exception. The contract requires exact parsing, no evaluator error and a review floor for all 75 cases from those three routine sources.

The reviewed classifier corrections also remove unrelated uncertain Git owners from exactly `git rev-parse --show-toplevel` and `git apply --check <literal-relative-patch-path>`. Their 50 corpus cases now retain the native review requirement without a fabricated terminal block or an allow proof. Other Git subcommands, routing options, unsafe paths and plain `git apply` retain their uncertainty. The fixture binds the updated compatibility and parser sources, including the new bounded wrapper and interpreter modules. Their sudo, encoded-stdin, literal-brace, interpreter and introspection corrections do not change the remaining corpus signatures. Every unchanged group still has to match its authored expectation and membership. The separate [catalog parity proof](evidence/declarative-extensions/catalog-parity-proof.v1.json) records the earlier baseline/candidate comparison with the same native engine; it has a different scope from the older Python oracle and these subsequent corrections.

The native contract records stronger behavior than the original oracle for 11,558 cases:

| Inherited limitation | Affected inputs | Cases above the original floor |
| --- | --- | ---: |
| Git compatibility uncertainty | Plain `apply` | 25 |
| Docker compatibility uncertainty | Container status inspection and `compose ps` | 50 |
| GitHub compatibility uncertainty | Resolve-review-thread mutation | 25 |
| Unsupported compatibility context | `PATH` override template | 4,167 |
| Destructive-shell compatibility uncertainty | Adversarial pipeline with a `dd` sink | 1,042 |
| Unsupported substitution or redirect parsing | Adversarial substitutions and redirected pipeline variants | 6,249 |

This includes 100 of the 1,000 benign cases and 11,458 of the 50,000 adversarial cases. Across the full corpus, 27,084 cases retain `native_command_evaluation_failed`; many already have an original oracle floor of `block`. Those errors are counted and reported. A validated, exactly bound native denial may contribute its terminal block to the host decision without inventing rule observations or an allow proof. Compiler, transport, binding or unknown evaluation failures do not qualify as expected inherited behavior.

The gates require exact native-contract equality, zero decisions below the original oracle floor, and unchanged decisions when the same native evidence passes through current and proposed effect composition. Reports retain every original-oracle divergence and its case digest. Passing the native contract does not mean equality with the original oracle's empty known-gap set; the report states that original equality is false. These diagnostics also do not establish installed-platform qualification, benign-workflow usability, SLO/soak performance, or release readiness. Improvements to the inherited limitations require a separate reviewed parser or classifier change and an explicit contract update.

The ten minimal pairs are a separate 20-command characterization. Their frozen fixture retains the original semantic labels, single-delta assertions and historical Python observations. The tests check explicitly recorded raw native floors and verify that host composition does not lower those floors. They do not claim equality with every semantic label: an exact native read can carry an allow proof, while approval context and capability consumption require evidence beyond these command strings.
